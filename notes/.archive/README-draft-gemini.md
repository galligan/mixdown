# 💽 Mixdown: A Modern Toolbox for AI/Agentic Prompting

Mixdown is a project that consists of two parts:

1.  A Node.js app with an API, CLI, and potentially other integrations for creating and managing prompts/instructions for AI chatbots, agents, and agentic development tools.
2.  A Markdown-based markup specification for creating effective, reusable, and maintainable prompts with reliable results.

## What is Mixdown?

If you're here, you're likely using AI coding tools like Cursor, Aider, or others Mixdown is [designed to work with](#mixdown-supported-targets). Each tool often requires context, guidance, and instructions in its own specific format (e.g., Cursor's `.cursor/rules`, Aider's `aider.conf.yml`, etc.).

Managing these different formats, behaviors, and capabilities across tools can quickly become complex and repetitive. You might even be tempted to stick to just one tool, missing out on the unique strengths of others. That's where Mixdown comes in.

**Terminology Note**: Mixdown uses the term **artifact** to mean the concrete file(s) it generates for each target tool (Cursor rules, Aider config snippets, etc.). You’ll typically find them in a designated output directory (e.g., `prompts/artifacts/`).

Mixdown lets you apply the "Don't Repeat Yourself" (DRY) principle to your AI tool instructions. Instead of maintaining multiple, slightly different versions of the same guidance, you create a single **mix** file (`.md`). This mix acts as the "gold master" for your instructions. Mixdown then processes this mix to generate the specific files needed by each target tool, in their required format and location.

> **Analogy**: Think of Mixdown as "Terraform for AI prompts": declare your ideal prompt rules once, target various coding agents, and ensure every teammate (human or bot) uses the same authoritative instructions—no copy‑paste, no drift, just high‑quality, version‑controlled context.

## What's with the name?

We borrowed "Mixdown" from the music production world. A mixdown is when individual tracks (vocals, drums, guitar) are combined into the final stereo song everyone hears. Similarly, Mixdown takes your core instructions and "mixes them down" into the specific formats required by different AI tools like Cursor, Aider, and beyond.

## Glossary of Terms

*(Based on the simplified syntax)*

* **Mix**: The source file (`.md`) containing instructions written in Mixdown's Markdown-based syntax. It's the "gold master" template. *Note: While standard Markdown, it contains Mixdown-specific syntax like `{{...}}` sections and `{...}` placeholders.*
* **Artifact**: The output file(s) generated by Mixdown for a specific **target** tool (e.g., `.mdc` for Cursor Rules, `.md` for Roo Code).
* **Target**: A specific AI tool or platform Mixdown can generate artifacts for (e.g., `cursor`, `aider`).
* **Section**: A block of content within a mix, delimited by `{{section_name ...}}` and `{{/section_name}}` (or self-closing `{{section_name ... /}}`). Sections organize content and can have attributes controlling their behavior.
* **Frontmatter**: Standard YAML block at the beginning of a `.md` mix file (between `---` lines) containing metadata like `name`, `description`, `targets`, and target-specific overrides.
* **Placeholder**: Dynamic tokens within a mix that get replaced during the build process.
    * `[AI placeholder]`: Instruction for the AI to fill in (passed through).
    * `{@alias_name}`: Inserts the value of a defined alias.
    * `{=data.key}`: Injects data from YAML files (e.g., `prompts/data/data.yaml`).
    * `{>mix_name#section_id|Link Text}`: Creates a link to another mix file (e.g., `mix_name.md`) or section, intelligently handling target-specific paths.
* **Mixin**: A way to include content from other files (includes, other mixes, templates) into the current mix, using the `{{$...}}` syntax (e.g., `{{$include:partial}}`, `{{$mix:base-rules}}`). Included files often also use the `.md` extension.
* **Attribute**: Key-value pairs or flags within a section's opening tag (`{{section key="value" flag}}`) that modify its behavior (e.g., `title`, `export`, `filter`, target-specific overrides like `title@cursor="..."`).
* **Target Group**: Predefined collections of related targets (e.g., `ide`, `cli`) used for shorthand filtering in attributes (`export="cli"`).

## Quick Start

### Set up Mixdown within a project

```bash
mixdown init
```

This command typically creates a `prompts` directory and potentially a `.mixdown` configuration directory:

```txt
project-root/
├── prompts/
│   ├── artifacts/      # Generated artifacts (may be elsewhere depending on targets)
│   │   ├── builds/     # Optional: Build-specific artifacts
│   │   └── latest/     # Optional: Symlink to the latest artifact set
│   ├── mixes/          # Your mix files (or 'instructions/')
│   │   ├── my-rule.md  # Mix file using .md extension
│   │   └── common/
│   │       └── base.md # Another mix file
│   ├── includes/       # Reusable content fragments for mixins
│   │   └── legal.md    # Include file using .md extension
│   ├── data/           # YAML data files for {=...} placeholders
│   │   ├── project.yaml
│   │   └── user.profile.yaml # Example profile data
│   └── templates/      # Optional: Template files for mixins
│       └── report.template.md # Template using .md extension
└── .mixdown/           # Mixdown configuration and cache
    ├── config.yaml     # Project-specific Mixdown configuration
    ├── cache/          # Cache directory
    └── reports/        # Build reports
```

*(Directory structure may vary based on configuration and evolving practices)*

## Creating Mixes (`.md` files)

Mixes are the core of Mixdown. They are Markdown files (`.md` extension) that use special syntax (`{{...}}` sections, `{...}` placeholders) for structure, dynamic content, and target-specific adaptations.

### Standard Frontmatter

Every mix starts with standard YAML frontmatter enclosed in `---`:

```yaml
---
# Required Mixdown metadata
mixdown:
  version: 0.1.0 # Version of the Mixdown spec this file adheres to
  name: core-coding-standards # kebab-case identifier for this mix
  description: "Establishes baseline coding standards for the project."

# Optional standard keys
labels: ["core", "linting", "best-practices"]
targets: ["cursor", "roo-code", "aider", "!windsurf"] # Explicitly include/exclude targets
# targets: ["all"] # Target all configured tools

# Target-specific overrides
cursor:
  description: "Cursor-specific rules for coding standards." # Overrides mixdown.description for cursor
  globs: ["**/*.ts", "**/*.tsx"] # Cursor-specific setting
  alwaysApply: true
aider:
  # Aider might use different keys or structures
  linting_prompt: "Apply these coding standards during code generation."

# Custom keys (ignored by Mixdown build, useful for humans/other tools)
author: Matt
created: 2025-04-23
---

# Mix Content Starts Here

This is the main body of your mix...
```

**Key Frontmatter Sections:**

* `mixdown`: Contains essential Mixdown metadata (`version`, `name`, `description`).
* `targets`: (Optional) A list of target IDs to include or exclude (prefix with `!`). If omitted, Mixdown might target all configured tools or rely on project settings.
* **Target-Specific Keys** (e.g., `cursor`, `aider`): Allows overriding top-level keys or providing settings unique to that target. The structure under a target key often mirrors what that tool expects in its configuration.
* Other keys (`labels`, `author`, etc.) are generally for informational purposes unless specifically interpreted by Mixdown or a target provider.

### Section Delimiters `{{...}}`

Mixdown uses double braces `{{ }}` to define logical sections within your Markdown content. This helps structure the prompt and allows for applying attributes.

```markdown
{{system}}
You are a helpful coding assistant. Follow the instructions precisely.
{{/system}}

{{instructions title="Code Formatting Rules" filter="target=ide"}}
- Use 4 spaces for indentation.
- Max line length is 100 characters.
{{/instructions}}

{{example title="Good Example" id="good-formatting"}}
```typescript
function hello(name: string): string {
    return `Hello, ${name}!`;
}
```
{{/example}}

{{bad-example title="Bad Example" filter="!target=cli"}}
```typescript
function hello( name: string ): string {
return \`Hello, ${name}!\`; // Inconsistent spacing
}
```
{{/bad-example}}

{{output-format format="code" language="json" /}}
```

**Syntax:**

* **Opening Tag:** `{{section_name attribute="value" flag}}`
* **Closing Tag:** `{{/section_name}}` (Optional if immediately followed by another opening tag)
* **Self-Closing Tag:** `{{section_name attribute="value" /}}`

**Common Sections (Examples):**

* `system`: System prompts.
* `instructions`: Specific instructions for the AI.
* `example`, `good_example`, `bad_example`: Demonstrative examples.
* `formatting`: Guidance on output format.
* `thinking`, `answer`: For chain-of-thought prompting.
* *You can define custom section names relevant to your domain.*

### Section Attributes

Attributes within the opening `{{...}}` tag control how a section behaves during the build process.

```markdown
{{guidelines
  title="Security Best Practices"
  title@cursor="Cursor Security Rules"
  export="cli"
  filter="!target=windsurf"
  id="security-rules"
}}
Content of the security guidelines...
{{/guidelines}}
```

**Common Attributes:**

* `title`: Adds a heading above the section content in the artifact.
* `id`: A unique identifier for linking (`{>#security-rules}`).
* `filter`: Controls inclusion/exclusion based on targets or groups (e.g., `filter="target=cursor,roo-code"`, `filter="group=ide"`, `filter="!target=aider"`).
* `export`: Exports the section to a separate artifact file for the specified targets/groups (e.g., `export="cli"`, `export="all"`). If `true` or no value, exports for all applicable targets.
* `format`: Renders the section content differently (e.g., `format="code"`, `format="blockquote"`).
* `no-xml`: (If applicable) Prevents wrapping the section in XML-like tags in the output artifact, potentially per-target (`no-xml="cursor"`).
* `remove-first-heading`: Strips the first Markdown heading found within the section's content.
* **Target-Specific Overrides:** Append `@target_id` or `@group_name` to an attribute to provide a specific value for that target/group (e.g., `title@cursor="Cursor Title"`).

### Placeholders `{...}`

Placeholders allow for dynamic content injection.

1.  **AI Placeholders `[...]`:**
    * Syntax: `[Describe what the AI should fill in]`
    * Purpose: Passed through directly to the AI as instructions. Mixdown doesn't replace these.
    * Example: `Please generate a commit message summarizing these changes: [summary]`

2.  **Alias Placeholders `{@...}`:**
    * Syntax: `{@alias_name}`
    * Purpose: Replaced by the value of a defined alias. Aliases can be defined in the mix frontmatter, project config, or global config.
    * Example: `Project Name: {@project-name}` -> `Project Name: Mixdown`
    * Built-ins: `{@target}` (current target ID), `{@target.name}` (current target display name).

3.  **Data Placeholders `{=...}`:**
    * Syntax: `{=file.key.path}`
    * Purpose: Injects data from YAML files located in `prompts/data/`.
    * Example: `{=user.email}` looks for `email` key in `prompts/data/user.yaml`. `{=project.details.repoUrl}` looks for `repoUrl` under `details` in `prompts/data/project.yaml`.

4.  **Internal Link Placeholders `{>...}`:**
    * Syntax: `{>mix_name}` or `{>#section_id}` or `{>mix_name#section_id|Link Text}`
    * Purpose: Creates links to other mixes (e.g., `mix_name.md`) or sections within the same/different mix. Mixdown resolves the correct path/format for the target artifact.
    * Example: `See the {>style-guide|Style Guide} for details.` -> `See the [Style Guide](style-guide.mdc)` (for Cursor) or `See the [Style Guide](style-guide.md)` (for Roo Code).
    * Use `mode="source"` to link to the source `.md` file: `{>my-rule mode="source"}` -> `[my-rule](../prompts/mixes/my-rule.md)`.

### Mixins `{{$...}}`

Mixins include content from other files or sources, typically also `.md` files.

```markdown
---
# Frontmatter...
---

{{$include:header}}
# Main Content

This mix builds upon the base rules.

{{$mix:base-rules title?h+="Base Rules Section" no-mixins}}
{{$template:report-format}}
{{$include:path="docs/CONTRIBUTING.md" sections="guidelines,!setup"}}
{{$include:@git-branch}}
{{$include:footer}}
```

**Syntax:** `{{$type:source_name attribute="value"}}`

* **`$include`**: Includes content from `prompts/includes/{source_name}.md` or using `path=`.
* **`$mix`**: Includes content from another mix file (`prompts/mixes/{source_name}.md`). By default, ignores the source mix's frontmatter and processing attributes unless specified.
* **`$template`**: Includes content from `prompts/templates/{source_name}.template.md`.
* **`@runtime`**: (Hypothetical) Includes dynamic info like `{{$include:@git-branch}}`.

**Common Mixin Attributes:**

* `title`, `title?h+`, `title?replace`: Modify the heading of the included content.
* `no-title`: Remove the main title/heading from the included content.
* `no-mixins`: Prevent processing of nested mixins within the included source.
* `sections`: Filter which sections from the source file to include (`sections="intro,conclusion,!details"`).
* `alias-from="source|current"`: Control which set of aliases (from the source file or the current file) are used when resolving placeholders within the included content.

## Advanced Topics

* **Target Groups**: Use predefined (`ide`, `cli`) or custom groups in attributes (`filter="group=my-editors"`) for easier targeting. Configure in `.mixdown/config.yaml`.
* **Heading Level Control**: Configure default heading levels, H1 reservation, and case globally (`.mixdown/config.yaml`) or per-file (frontmatter `heading_level` key).
* **Attribute Modifiers**: Use `?` modifiers for advanced control, like `title?h2="Explicit H2"` or `title?replace`.
* **Build Process**: Use `mixdown build` to generate artifacts. Use `mixdown preview --target cursor` (or similar) to see output without writing files.
